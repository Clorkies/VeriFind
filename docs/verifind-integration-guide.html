02 — Technical Implementation

Cardano Ledger Integration

How the server-side Next.js route uses MeshJS to build, sign, and submit metadata transactions to the Cardano Preview network — without requiring student wallets.

1
Wallet & Provider Init

Located in app/api/ledger/anchor/route.ts. We initialize a headless wallet using the server's mnemonic and connect it to Blockfrost.

Server-side Setup
.ts
const provider = new BlockfrostProvider(process.env.BLOCKFROST_PROJECT_ID);

const wallet = await MeshCardanoHeadlessWallet.fromMnemonic({
  mnemonic: process.env.CARDANO_ADMIN_MNEMONIC.trim().split(/\s+/),
  networkId: 0, // 0 for Preview, 1 for Mainnet
  walletAddressType: AddressType.Base,
  fetcher: provider,
});

const changeAddress = await wallet.getChangeAddressBech32();
2
Metadata & Tx Building

We construct a JSON object with event details, attached to the transaction under the CIP-20 standard label 674.

Because this is an anchor transaction, we send 2,000,000 Lovelace back to our own change address to satisfy protocol rules.

Transaction Construction
.ts
const metadata = {
  app: "verifind",
  event: body.event, // e.g. "claim.approved"
  itemId: body.itemId,
  claimId: body.claimId ?? null,
  adminId: body.adminId,
  timestamp: new Date().toISOString(),
};

const tx = new Transaction({
  initiator: wallet as any, // Cast bypasses beta version mismatch
  fetcher: provider,
  submitter: provider,
  evaluator: provider,
})
  .sendLovelace(changeAddress, "2000000")
  .setMetadata(674, metadata);
3
Sign & Submit

The headless wallet signs the built transaction autonomously. We broadcast it to the network via Blockfrost and return the hash to the frontend.

Network Broadcast
.ts
const unsignedTx = await tx.build();
const signedTx = await wallet.signTxReturnFullTx(unsignedTx);
const txHash = await provider.submitTx(signedTx);

return Response.json({ txHash });
4
Saving the Anchor

In ItemsProvider.tsx, after the database mutation, we trigger the API route and save the resulting hash back to Supabase.

Frontend Context Action
.tsx
// Example from approveClaim()
const txHash = await anchorLedger({
  event: "claim.approved",
  itemId: claim.item_id,
  claimId: claimId,
  adminId: adminId,
});

// Save TxHash to database for public verification
await supabase
  .from("items")
  .update({ tx_hash: txHash })
  .eq("id", claim.item_id);
5
Public Verification

On Item Cards, we use the saved transaction hash to generate a direct link to a blockchain explorer, proving the event occurred on-chain.

03 — User Experience

Operational Roles & Flows

Detailed step-by-step interaction guide for both administrators and students using the VeriFind platform.

Admin Workflow

The staff-led intake and verification process.

1. Intake: Staff logs the item (e.g., "Silver Watch") and adds a Secret Description (e.g., "Engraved 'To John' on the back").
2. Review: Staff compares incoming student claims against the secret. If the student mentions the engraving, it's a match.
3. Approval: Clicking 'Approve' updates the registry and anchors the decision to the Cardano ledger.
4. Release: Upon student arrival, staff verifies the physical Student ID and releases the item.
Student Workflow

The user discovery and retrieval journey.

1. Discovery: Student browses the public board at /board and identifies their lost item.
2. Claiming: Student submits a claim with their Student ID and describes the item's unique features.
3. Tracking: Student visits /my-claims to track the progress of their request in real-time.
4. Retrieval: Once approved, the student visits the office with their ID card to collect the item.
